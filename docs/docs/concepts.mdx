Everything in Vexum composes from a handful of primitives. A unit of work — a **dispatch** — is one [agent](#agent), in one [container](#container), over a person's [workspace](#workspace), authorized by an [identity](#identity) token, fired by the [scheduler](#scheduler).

## Workspace

A git **folder**, stored in an (encrypted) bucket, with an `id` and an access **mode** (`ro`/`rw`). It holds knowledge and plans — all just files, with **no dictated structure**. git is the durable state and the undo.

Workspaces are **flat and equal-rank**: your Personal workspace is just one workspace among any you create or join — activatable and deactivatable like the rest, with no special "baseline" status. The **active set** — the ordered list of workspaces you currently have switched on — is the single source of truth for what an agent mounts and what the client shows; every read is addressed by the workspace's slug. The first active workspace is the agent's working directory for the turn.

A dispatch mounts the active set inside a **three-tier stack**: `_global` (ro — platform behaviour, shared by everyone) \+ your active workspaces (rw where granted) \+ `_system` (rw — private per-user state: who you are, settings, routines, and your **chat sessions**, which live here rather than in any workspace so a shared workspace never carries your private conversations).

A workspace can be **shared**: invite others and their agents mount it alongside their own, with per-member roles. Cross-references between entities are `[[wikilinks]]` — the client renders them as clickable entity chips and resolves them across every active workspace.

The knowledge itself lives in the `kg/` subtree as an [Open Knowledge Format](https://github.com/GoogleCloudPlatform/knowledge-catalog/tree/main/okf) (OKF) v0.1 bundle — one markdown file per entity at `kg/entities/<type>/<slug>.md`, YAML frontmatter on top, `index.md` listings for navigation. Knowledge-as-code: portable, diffable, and readable by any OKF consumer, not just Vexum. See [Browse the workspace](/how-to/workspace-files#the-knowledge-graph-is-an-okf-bundle).

## Agent

A generic CLI coding agent selected by a **runner** (Claude Code is one; others and BYO-inference plug in the same way). It works the mounted workspace with a scoped toolbelt and commits. It is **untrusted** — outside the trust boundary — so it carries a signed token but enforces nothing. Its outbound capabilities (email, calendar, web) are **integrations**: cred-gated tools reached over MCP, never built into the backend. See [Agents](/core/agents).

## Container

The isolated, ephemeral unit an agent runs in, spawned by the [runtime](/core/runtime). Sub-second to start, reaped on idle, no egress except through brokered tools — thousands run in parallel with no lateral movement. Its live output streams to the client over a per-dispatch channel.

## Identity

The chain of custody. The launcher proves itself (a user session, or a signed delegation grant for a schedule/integration); the identity service mints a **short-lived signed dispatch token** (_subject_ = on whose behalf · _launcher_ = who triggered · scope); the runtime **attests the workload** (SPIFFE/SPIRE); and **every boundary verifies** the token — never the agent. Tool calls exchange it for an audience-scoped credential (Keycloak / RFC 8693) at an MCP gateway, so the agent never holds a raw key.

## Scheduler

Redis. The one mechanism that **dispatches agents**, on a trigger — a schedule entry (cron), an integration event (e.g. new email), or _now_ (chat). It holds the user-manageable schedule; a meeting ending is just another event that dispatches an agent.
